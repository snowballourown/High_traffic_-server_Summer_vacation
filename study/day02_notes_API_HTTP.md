## HTTP 메서드의 속성 

* 안전
* 멱등 
* 캐시가능 

1. ####  Safe(안전)
- 호출해도 리소스가 변경하지 않는다 
- Q: 그대로 계속 호출해서, 로그 같은게 쌓여서 장애가 발생하면요? 
- A: 안전은 해당 리소스만 (변하냐? 안변하냐? )고려한다. 그런 부분까지는 고려 x 

2. #### 멱등(Idempotent)
- f(f(x)) - f(x)
- 한번 호출하든 두 번 호출하든 100번 호출하든 결과가 똑같다 
- 멱등 메서드 
  - GET: 한 번 조회하든. 두 번 조회하든 같은 결과가 조회된다. 
  - PUT: 결과를 때체한다. 따라서 같은 요청을 여러번 해도 최종 결과는 같다 -> 같은걸로 계속 교체하니 결과가 똑같다 
  - DELETE: 결과를 삭제한다. 같은 요청을 여러번 해도 삭제된 결과는 같다 -> 같은것을 계속 삭제 시도를 하는거니 여러번해도 삭제된 결과가 같음 
  - POST: 멱등이 아니다! 두 번 호출하면 같은 결제가 중복해서 발생할 수 있다.(배송을 두번 등)


멱등이 why 필요한가???
 - 자동 복구 매커니즘 
 - 서버가 TIMEOUT등으로 정상응답을 못 주었을때, 클라이언트가 같은 요청을 다시 해도 되는가? 판단 근거

Q: 재요청 중간에 다른 곳에서 리소스를 변경해버리면?    
A: 멱등은 외부 요인으로 중간에 리소스가 변경되는 것 까지는 고려하지는 않는다

### 상태코드

* 1xx(Informational) : 요청이 수신되어 처리중  
* 2xx(Success) : 요청 정상 처리
* 3xx(Redirection) : 요청을 완료하려면 추가 행동이 필요
* 4xx(Client Error) : 클라이언트 오류, 잘못된 문법등으로 서버가 요청을 수행할 수 없음 
* 5xx(Server Error) : 서버오류, 서버가 정상 요청을 처리하지 못함 


---
#### 2xx case 

- 201 Created : 요청 성공해서 새로운 리소스가 생성됨 (POST로 등록 해서 등등) 
- 200 OK : 요청성공(조회 등등)
- 202 accepted : 요청이 접수는 됐으나 처리가 완료되지 않음(잘사용되지는 않음)
- 204 No content : 서버가 요청을 성공적으로 수행했지만, 응답 페이로드 본문에 보낼 데이터가 없음 
    - ex) 웹 문서 편집기에서 save버튼
    - save 버튼의 결과로 아무 내용이 없어도 된다.(굳이 돌려줄필요가없기에)
    - save 버튼을 눌러도 같은 화면을 유지해야 한다.
    - 결과 내용이 없어도 204 메세지(2xx)만으로 성공을 인식할 수 있다.

#### 3xx case 
301 ~ 308까지 중요  
###### redirection(리다이렉션이란?) : 
웹 브라우저는 3xx 응답의 결과에 location 헤더가 있으면, 
Location 위치로 자동 이동(리다이렉트)
- 영구 리다이렉션- 특정 리소스의 URI가 영구적으로 이동(이제 완전히 바꿨다고하는거임)
  - ex) /member -> /users
  - ex) /event -> /new-event
- 일시 리다이렉션- 일시적인 변경
  - 주문 완료후 주문내역으로 이동 
  - PRG: POST/Redirect/GET
- 특수 리다이렉션 
  - 결과 대신 캐시를 사용 


##### 영구 리다이렉션 
301, 308  
원레 URL를 사용x ,검색 엔진등에서도 변경 인지
- 301 Moved Permanently
    - 리다이렉트 요청 메서드가 (POST ->GET)으로 변하고, 본문이 제거될 수 있음(MAY)    
    - 삭제가 되서 다시 본문을 입력해야될 수 도 있음
       
- 308 Permanent Redirect
    - 301과 기능은 같음 
    - 리다이렉트시 요청 메서드와 본문 유지(처음 POST를 보내면 리다이렉션으로)
    - POST는 본문도 살려서 보내줌 => 하지만 URI가 바뀌면 형식 다바껴서 그냥 301로 쓰는게 나을수도있다함 

##### 일시적인 리다이렉션 
302, 307, 303   
리소스의 URI가 일시적으로 변함
따라서 검색 엔진등에서 URL을 변경하면 안됨

- 302 FOUND (실무에서 많이씀)
    - 리다이렉션시 요청 메서드가 GET으로 변하고, 본문이 제거 될 수 있음{대부분 변함}
- 307 Temporary Redirect
  - 302 와 기능은 같음
  - 리다이렉션시 요청 메서드와 본문 유지(요청 메서드를 변경하면 안된다. MUST NOT)
- 303 See other
  - 302와 기능은 같음
  - 리다이렉트시 요청메서드가 GET으로 변경 {GET으로 무조건 유지}

    

##### PRG: POST/Redirect/GET
일시적인 리다이렉션 - 예시

- POST로 주문후에 웹 브라우저를 새로고침하면?
- 새로고침은 다시 요청(결제 완료페이지에서 )
- 중복 주문이 될 수 이다 (문제 발생, redirect를 다른곳으로 해주지않아서 새로고침으로 다시 요청이 보내지는경우)

=> 방지    

* POST로 주문후에 새로 고침으로 인한 중복 주문 방지
* POST로 주문후에 주문 결과 화면을 GET 메서드로 리다이렉트
* 새로고침해도 결과 화면을 GET으로 조회
* 중복 주문 대신에 결과 화면만 GET으로 다시 요청 (해결법)

##### 기타 리다이렉션


* 304 Not Modified
  * 캐시를 목적으로 사용
  * 클라이언트에게 리소스가 수정되지 않았음을 알려준다. 따라서 클라이언트는 로컬PC에 저장된 캐시를 재사용한다.
    (캐시로 리다이렉트한다.)
  * 304응답은 응답에 메세지 바디를 포함하면 안된다.(로컬 캐시를 사용해야하므로)
  * 조건부 GET, HEAD 요청시 사용

#### 4xx case 
클라이언트 오류

* 클라이언트의 요청에 잘못된 문법등으로 서버가 요청을 수행할 수가 없음
* 오류의 원인이 클라이언트에 있음
* 중요! 클라이언트가 이미 잘못된 요청, 데이터를 보내고 있기 때문에, 똑같은 재시도가 실패함


* 400 : 클라이언트가 잘못된 요청을 해서 서버가 요청을 처리할 수 없음
    - 요청 구문, 메세지 등등 오류
    - 클라이언트는 요청 내용을 다시 검토하고, 보내야함
    - ex) 요청 파라미터가 잘못되거나, API스펙이 맞지않을때

* 401 UnAnthorized : 클라이언트가 해당 리소스에 대한 인증이 필요함
    - 인증(Authentication) 되지않음
    - 401 오류발생시 응답에 WWW-Authenticate헤더와 함께 인증 방법을 설명
    - cf
      - 인증 : 본인이 누구인지 확인, (로그인)
      - 인가 : 권한부여(ADMIN 권한처럼 특정 리소스에 접근할 수 있는 권한, 인증이 있어야 인가가 있음, 로그인한후에 사람마다에 권한까지에 등급) 
      - 오류 메세지가 Unauthorized 이지만 인증 되지않음(이름이 아쉬움, 로그인이안됐다)

* 403 Forbidden : 서버가 요청을 이해했지만 승인을 거부함
    - 주로 인증 자격 증명(로그인이 됐지만)은 있지만, 접근 권한이 불충분한경우
    - ex)어드민 등급이 아닌 사용자가 로그인은 했지만, 어드민 등급의 리소스에 접근하는 경우
  
* 404 Not Found : 요청 리소스를 찾을 수 없음
    - 요청 리소스가 서버에 없음
    - 또는 클라이언트가 권한이 부족한 리소스에 접근할 때 해당 리소스를 숨기고 싶을 때(권한이 없는애한테 존재자체를 숨기고싶을떄)

#### 5xx 
서버 오류 -> 만들면 안됨(백엔드) 

* 서버 문제로 오류 발생
* 서버에 문제가 있기 때문에 재시도 하면 성공할 수도 있음(복구가 되거나 등등)


* 500 Internal Server Error  
서버 문제로 오류 발생, 애매하면 500오류
    - 서버 문제 문제로 오류 발생
    - 애매하면 500오류

* 503 Service Unavailable  
서비스 이용 불가
    - 서버가 일시적인 과부하 or 예정된 작업으로 잠시 요청을 처리할 수 없음
      - Retry-After 헤더 필드로 얼마뒤 복구되는지 보낼 수도 있음
